# Product Intent Specification — Selective Structured Output

## Source

- Tracker: GitHub
- ID: #26 — `[SLDD-01] Specify selective structured output for AI flows`
- URL: https://github.com/Ivictors/ai-ecommerce-assistant/issues/26
- Snapshot date: 2026-09-29

## Goal

Provide predictable JSON responses for assistant flows that will be consumed
by the future frontend, while preserving natural text for general
conversation. The backend must validate and enrich structured results using
authoritative application data instead of trusting values generated by the
language model.

## Target Users

- Customer using the chat assistant.
- Future Angular frontend consuming predictable response fields.
- Backend application services validating business data.

## Success Metrics

- The chat endpoint returns a single documented JSON envelope for every flow.
- Frontend-consumed product, order, and policy flows expose predictable type
  and data fields.
- General conversation remains available without forcing a business schema.
- No price, stock, order status, ownership, payment, or authorization value is
  accepted solely from model output.
- Invalid or incomplete model classifications result in safe fallback behavior.

## Acceptance Criteria (EARS-lite)

- AC-001: The chat endpoint shall return a JSON response envelope containing a
  response type, schema version, and user-facing message.
- AC-002: When the assistant handles general conversation, the system shall
  return a `TEXT` response without requiring a business-data payload.
- AC-003: When the assistant handles a product-information flow, the system
  shall return a typed product response containing data obtained from the
  authoritative backend product capability.
- AC-004: When the assistant handles an order-status flow, the system shall
  return a typed order response containing data obtained after ownership
  validation.
- AC-005: When the assistant handles a policy-information flow with relevant
  approved knowledge, the system shall return a typed policy response grounded
  in that knowledge.
- AC-006: If a policy-information flow has no relevant approved knowledge, then
  the system shall return a safe response that does not assert an unsupported
  policy.
- AC-007: If the model returns an unknown, incomplete, or incompatible intent,
  then the system shall use a deterministic safe fallback or request
  clarification.
- AC-008: The system shall not accept model output as authoritative for price,
  stock, order status, ownership, payment, or authorization.
- AC-009: The response envelope shall expose a schema version so compatible
  future changes can be introduced deliberately.
- AC-010: The system shall preserve backend authentication and ownership checks
  for structured responses.

## Non-Goals

- Returning every assistant response as a domain-specific schema.
- Allowing the LLM to construct authoritative product or order data.
- Implementing the Angular frontend in this phase.
- Replacing ProductTool, OrderTool, ProductService, OrderService, or RAG
  retrieval with model-generated values.
- Designing payment, inventory, return, or promotion response schemas.
- Supporting multiple public API versions in the first implementation.

## Non-Functional Requirements

No quantitative non-functional requirements are approved for this phase.
Response compatibility and validation behavior are functional requirements.

## Glossary

- **Structured output** — A response with a documented JSON shape and typed
  fields.
- **Response envelope** — Common JSON fields shared by every chat response.
- **Response type** — Discriminator identifying text, product, order, or policy
  content.
- **Schema version** — Version identifying the public response contract.
- **Free-form response** — Natural-language response represented by the `TEXT`
  response type.
- **Authoritative data** — Business data obtained from trusted backend
  application capabilities.
- **Fallback** — Safe behavior used when model classification is invalid,
  incomplete, unsupported, or insufficient.

## Risks and Assumptions

- Changing the current `text/plain` response to a JSON envelope affects future
  clients and requires contract tests.
- The model may produce syntactically valid but semantically invalid intent
  values; validation must occur before routing.
- Structured responses can improve frontend reliability but must not bypass
  existing authentication or ownership boundaries.
- The first response envelope uses one endpoint and one initial schema version.

## Resolved Questions

- **Q-001:** Which structured-output scope is approved?
  - Resolution: "estrategia 3" — structured schemas only for predictable
    frontend-consumed flows, with free-form conversational responses retained.
  - Resolved at: 2026-09-29

- **Q-002:** Which initial API compatibility strategy is approved?
  - Resolution: "estrategia 3" — keep one chat endpoint and return a JSON
    envelope discriminated by response type.
  - Resolved at: 2026-09-29

## Open Questions

None. Exact DTO fields and routing interfaces belong to the approved technical
design and low-level contract phases.
