# High-Level Technical Design — Authenticated Conversation Creation

## Architecture Diagram

```text
HTTP POST /api/conversations (no owner field/body)
        |
        v
ConversationResource (@RolesAllowed USER)
        |
        +--> CurrentUserService --> verified numeric JWT subject
        |
        v
ConversationService (@Transactional)
        |                         |
        v                         v
UserRepository             ConversationRepository
        |                         |
        +---- User entity --------+
                    |
                    v
       Conversation(user, createdAt)
                    |
                    v
       ConversationResponse (201)
```

## Component Responsibilities

- `ConversationResource` owns the REST method, extracts the authenticated
  numeric identity, and maps the result to HTTP 201 with the existing response
  DTO. It does not accept an owner ID from the client.
- `CurrentUserService` remains the source of the caller ID from the verified
  JWT principal.
- `ConversationService` coordinates the use case: load the authenticated user,
  create the domain conversation, and persist it within a transaction.
- `UserRepository` resolves the persisted `User` corresponding to the numeric
  subject.
- `ConversationRepository` persists the new conversation and retains existing
  owner-filtered reads.
- `ConversationResponse` remains the response shape: `id`, `userId`, and
  `createdAt`.

## API Contract Sketch

`POST /api/conversations`

- Authentication: required; caller must have the `USER` role.
- Request: no request body and no owner-selection field. Any owner association
  is derived from the authenticated identity.
- Success: `201 Created`, JSON `ConversationResponse`:

```json
{
  "id": 25,
  "userId": 7,
  "createdAt": "2026-10-05T12:00:00Z"
}
```

- No `Location` header is proposed because the resource currently has no
  `GET /api/conversations/{id}` endpoint; the response body provides the
  identifier and the existing collection endpoint provides the user's list.
- Unauthenticated: existing `401 UNAUTHENTICATED` API error.
- Authenticated without required role: existing `403 FORBIDDEN` API error.
- Unexpected persistence failure: existing generic `500` error behavior.

Existing endpoints remain unchanged:

- `GET /api/conversations` returns only conversations for the authenticated
  user.
- `POST /api/chat?conversationId={id}` requires an ID and performs the
  existing owner-scoped lookup before assistant processing.

## Data Flow

1. Quarkus validates the JWT and enforces the `USER` role.
2. The resource asks `CurrentUserService` for the verified numeric subject.
3. The application service loads that persisted `User` and creates a domain
   `Conversation` associated with it.
4. The application service persists the entity within the transaction.
5. The resource maps the persisted entity to the existing response DTO.
6. The client receives the database-generated identifier and can use it in the
   existing chat request.

No client-provided owner value participates in this flow.

## Data Model Overview

- Reuse `Conversation` and the existing `conversations` table.
- `id` remains generated by the database; `user_id` references the persisted
  user; `created_at` is set by the existing domain constructor.
- No Flyway migration or data backfill is expected.
- Hibernate validation remains enabled to detect future entity/schema drift.

## Security Posture

- Apply the existing class-level `@RolesAllowed("USER")` boundary to the new
  operation.
- Use only the verified JWT subject for ownership, consistent with accepted
  ADR-002 in `.specs/security-authorization/adr/ADR-002-ownership-application-boundary.md`.
- Keep the use case's user ID explicit so existing chat ownership validation
  remains applicable outside REST as well.
- Do not log access tokens or create any client-controlled owner parameter.
- Invalid/anonymous requests must fail before persistence.

## Observability Requirements

- Reuse existing request/error handling; no new metrics or logs are required
  for this single create operation.
- Do not log token claims or unnecessary customer data.
- Broader request correlation and metrics remain in issue #13.

## Key Trade-offs and Alternatives

- **Reuse existing response DTO vs create a new DTO:** reuse preserves the
  existing collection response contract and avoids duplicate representations.
- **Owner from token vs client owner field:** token-derived ownership follows
  approved security ADR-002 and prevents horizontal privilege escalation.
- **201 body without `Location` vs add a `GET /{id}` route:** use the response
  body and current list endpoint; a single-resource read endpoint is outside
  the issue and can be specified separately if later needed.
- **No persistence schema change:** the domain entity/table already express
  the required relation and generated ID.

## Risks and Rollback

- A valid token whose user row was removed could fail user resolution. There
  is no user-deletion workflow in the current MVP; if that workflow is added,
  stale-subject semantics must be specified then.
- If owner assignment is mistakenly taken from input rather than the verified
  identity, another user's conversation could be created; tests explicitly
  inspect persisted ownership.
- Rollback is a code-only revert; no migration or stored conversation needs to
  be destructively removed.

## High-Level Test Scenario Map

- Happy path: authenticated USER creates a row and receives 201 plus generated
  ID/metadata.
- Ownership: the persisted owner equals the token subject even if the request
  attempts to supply a different owner ID.
- Visibility: the creator's collection includes the new conversation; another
  user's collection does not.
- Authentication: no/invalid token returns 401 and creates no row; a valid
  token without USER role returns 403.
- Chat isolation: another user submitting the new ID receives the existing
  not-found response before any LLM interaction.
- Compatibility: the creating owner resolves the ID through the existing
  owner-scoped chat lookup.
